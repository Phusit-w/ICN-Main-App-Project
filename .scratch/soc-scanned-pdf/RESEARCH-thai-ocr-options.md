# Thai OCR options for scanned SOC/TOR PDFs (research, 2026-10-15)

Scope: Thai+English, ruled-table cells (~2,000 cell PNGs/file, 300 DPI), Windows Server, no admin, no GPU, no Docker, no Claude API, no Google Cloud billing.
Time-boxed research: some items are marked UNVERIFIED. No published head-to-head Thai benchmark of Tesseract/EasyOCR/PaddleOCR on Thai table cells was found; the only Thai CER comparison is the small self-reported Thai-TrOCR card (104 images, PaddleOCR not included): https://huggingface.co/openthaigpt/thai-trocr . So any accuracy ranking below for non-LLM engines is NOT evidence-based; a 50-cell local test is needed.

## (a) Is Paddle slowness with oneDNN off on Windows CPU a known issue?

- The oneDNN crash `ConvertPirAttribute2RuntimeAttribute ... ArrayAttribute<DoubleAttribute>` is a known 3.3.x CPU regression; one write-up says versions before 3.2.x ran normally https://www.cnblogs.com/zmm521/p/18684355 and the issue thread https://github.com/PaddlePaddle/PaddleOCR/issues/17955 (paddleocr 3.4.1 + paddlepaddle 3.3.1: `enable_mkldnn=True` raised NotImplementedError). Env var `PADDLE_PDX_ENABLE_MKLDNN_BYDEFAULT=0` also disables it.
- The same issue #17955 (closed 2026-07-13) states the real cause of slow/huge-memory CPU inference: default detection resize (`limit_type="min"`, `limit_side_len=64`) only upscales, never downscales, so a 300 DPI page goes to the detector at near full size; maintainer says the SERVER detector needs about 5 GB per megapixel on CPU, 2.x capped the long side at 960. Workaround: `text_det_limit_type="max"`, `text_det_limit_side_len=960` (or lower max_side_limit e.g. 1600). So with cells it is the server detector on big images + mkldnn off that kills speed; rec-only avoids it.
- I did NOT find a verified statement that 3.2.x or 3.4+ fixes oneDNN on Windows. Pinning paddlepaddle below 3.3 (e.g. 3.2.x) is suggested by the blog but UNVERIFIED for Windows + your paddleocr 3.7.0 pairing (a version mismatch between paddleocr and paddlepaddle also caused the error for one user in the search results). The ONNX route (RapidOCR) avoids Paddle runtime entirely.

## (b) Skip detection, recognition only

- PaddleOCR 3.x `TextRecognition` module: `from paddleocr import TextRecognition; m = TextRecognition(model_name="th_PP-OCRv5_mobile_rec"); out = m.predict(input=np_array_or_path_or_list, batch_size=N)`; returns `rec_text`, `rec_score`. Input accepts ndarray, file path, URL, directory, list. https://www.paddleocr.ai/latest/en/version3.x/module_usage/text_recognition.html (docs show only a text-line example; running on cropped cells is an inference).
- Expected speedup: UNVERIFIED (no published number). Rec model is 7.5 MB and processes images resized to height 48 (general PP-OCR knowledge), so per-line cost should be tens-hundreds of ms vs seconds; the server detector on 300 DPI input is the dominant cost per the issue above. Expect order-of-magnitude, measure it. Caveat: the rec model reads ONE text line; cells with several lines need line splitting (horizontal projection on the cell) or else accuracy drops.
- RapidOCR equivalent: `RapidOCR(...)` with `use_det=False, use_cls=False` / call rec only (parameter names differ by version; UNVERIFIED, check docs).

## Ranked recommendation (best first)

1. **Hybrid: RapidOCR/Paddle rec-only (Thai v5 mobile) locally, escalate low-confidence cells to Typhoon API.** Both pieces exist and are free; local step fixes the speed problem, Typhoon (accuracy about Sonnet's per user) catches the rest within 20 req/min (up to ~500 calls per file = 25 min). Risk: rec_score calibration; line splitting.
2. **Azure Document Intelligence Read/Layout on whole pages** (Thai printed supported, F0 free 500 pages/month, no expiry). 85 pages/file -> ~5 files/month free; layout returns table cells so cell-cutting may be unnecessary. Risks: needs an Azure account (card), F0 PDF page limits UNVERIFIED, Thai table accuracy unknown.
3. **Typhoon API only, with batching** (several cells per image/montage) to stay under 20 req/min. Simple but accuracy of montage unverified, and 99 min if 1 cell/call.
4. Gemini free tier (whole page or montage): likely strong Thai OCR but free tier data is used to improve Google products, limits only visible in AI Studio, unverified.
5. Tesseract tha (portable) as a free cheap first pass: speed likely fine, Thai accuracy unknown; could replace the first stage of option 1 if it beats Paddle on your cells.
6. Local Typhoon open weights, EasyOCR, Surya: CPU too slow or heavy install. AWS Textract: no Thai. docTR: skipped.
